# Универсальный шаблон конечных почасовых задач с чанками, журналированием и восстановлением

**Версия:** 3.0 · **Дата:** 21.10.2026  
**Назначение:** постановка продолжительных накопительных работ в ChatGPT Scheduled Tasks или аналогичном планировщике, где каждый запуск получает собственную недолговечную среду, а результаты должны переживать сбои и повторные выдачи.  
**Область:** исследования и БЗ, код/рефакторинг, аналитика, научные расчёты, корпусная обработка, подготовка монографий и другие задачи, которые делятся на проверяемые части.  
**Принцип:** *один запуск — одна короткая восстанавливаемая транзакция; много запусков — одна конечная работа*.  
**Статус документа:** переносимый шаблон и операционная спецификация. Сам по себе не создаёт Scheduled Task и не гарантирует возможностей платформы.

> **Как пользоваться:** (1) заполнить параметры раздела A, (2) поместить постоянные ТЗ и исходные данные в долговременное доступное хранилище, (3) скопировать раздел B в текст **одного** задания, (4) настроить конечное почасовое расписание, (5) протестировать первые 2–3 запуска по разделу C. Не переносить ссылки, ID, KPI и сроки из примеров Conquest в новый проект.

```yaml
project:
  id: "<SHORT_STABLE_PROJECT_ID>"
  title: "<НАЗВАНИЕ>"
  objective: "<ОДНА конечная проверяемая цель>"
  in_scope: ["<что разрешено>"]
  out_of_scope: ["<что строго запрещено>"]
  definition_of_done: "<условия COMPLETE с доказуемыми метриками>"
  partial_final_policy: "PARTIAL_FINAL_BLOCKED + остаток + необходимые входы"

schedule:
  cadence: "FREQ=HOURLY"
  start_at_utc: "<UTC дата/время ПЕРВОГО будущего запуска>"
  max_nominal_slots: 48     # заменить нужным числом
  hard_deadline_utc: "<дата/время, после которых не продлевать>"
  task_id: "<ID существующей automation после создания; до создания UNKNOWN>"
  timezone_for_reports: "<IANA timezone>"
  no_reschedule_without_explicit_user_command: true

storage:
  rw_root_uri: "<ОДНА рабочая папка/репозиторий, явно разрешённые операции>"
  diagnostics_uri: "<дочерний путь/папка диагностики>"
  claims_uri: "<дочерний путь/папка заявок запусков>"
  checkpoints_uri: "<дочерняя папка immutable checkpoints>"
  read_only_sources:
    - "<точные URL/IDs всех исходных папок и объектов>"
  forbidden_write_locations: ["<все остальные, включая root облачного диска>"]
  local_user_disks_accessible: false
  persistent_source_bytes_required: true

inputs:
  primary_spec_uri: "<полное ТЗ>"
  scope_policy_uri: "<политика источников, прав и статусов>"
  initial_checkpoint_uri: "<только стартовый fallback; каждый раз искать свежее>"
  manifest_uri: "<реестр источников с IDs/хешами>"
  source_priority: ["<первичные>", "<утверждённые>", "<вторичные кандидаты>"]
  prohibited_tools: ["<если есть>"]

quality:
  kpi_1: "<проверенные сущности / честный знаменатель>"
  kpi_2: "<проверенные содержательные элементы / честный знаменатель>"
  kpi_3: "<принятые и воспроизводимые связи / QA / открытые P0>"
  status_ladder: ["CANDIDATE", "PARTIAL", "VERIFIED", "ACCEPTED"]
  source_provenance_required: true
  reproducible_restore_required: true
  acceptance_test_uri: "<критерии тестов; либо в ТЗ>"

budget:                 # рекомендуемый осторожный старт; менять по реальным замерам
  max_run_wall_minutes: 24
  claim_and_preflight_until_min: 2.5
  substantive_work_until_min: 12.5
  durable_wip_until_min: 15.5
  qa_until_min: 20.0
  remote_publish_until_min: 23.0
  final_marker_until_min: 24.0
  max_work_packages_per_run: 1
  retry_max_attempts_per_transient_resource: 3
  retry_total_seconds_per_resource: 30
  election_grace_seconds: 3
  predecessor_grace_minutes: 33
  auto_expand_after_success: false

  at_nominal_slots: [12, 24, 36]    # адаптировать под max_nominal_slots
  no_progress_triage_after_runs: 2
```

**Жёсткое различие времён:** `max_nominal_slots` ограничивает число **номинальных временных слотов**, а не количество внутренних повторов исполнения; `hard_deadline_utc` ограничивает календарь независимо от слотов. Запуск в ошибочном/дублированном слоте не даёт оснований расширять первоначальный бюджет. При создании повторяющегося расписания `DTSTART` должен указывать на **будущий** момент, не на уже прошедшую секунду. Не смешивать `COUNT` и `UNTIL` в одном RRULE: если нужен и предел числа запусков, и конечный срок, выбрать поддерживаемую конечную форму расписания и независимо проверять вторую границу внутри задания.

**Временной slot ID:** при наличии провайдерского `scheduled_for_utc` — использовать его; при фиксированном `DTSTART` и часовом шаге допустим `slot_index = floor((scheduled_occurrence - DTSTART)/3600)`. Нельзя в общем случае приравнивать *час фактического старта* к *номинальному слоту*: задержанный запуск может пересечь границу часа. Если привязать исполнение к слоту доказуемо нельзя, регистрировать `SLOT_UNCERTAIN`, не производить глобальных изменений.

## B. ИСПОЛНИТЕЛЬСКИЙ ПРОМПТ — скопировать в Scheduled Task после подстановки параметров

> **НАЧАЛО КОПИРУЕМОГО ПРОМПТА**

### 1. Цель и неизменяемые запреты

Каждый час продолжай конечный накопительный проект **«<TITLE>»**. Цель: **<OBJECTIVE>**. Выполняй только **<IN_SCOPE>**; никогда не выполняй **<OUT_OF_SCOPE>**. Работа должна приводить к одному интегрированному конечному результату, а не к независимым демонстрациям.

Максимум **<N> номинальных почасовых слотов**, с **<START_UTC>** до **<HARD_DEADLINE_UTC>**. НЕ создавай вторую задачу, НЕ обновляй/не продлевай расписание по собственной инициативе. При достижении `<COMPLETE_STATUS>` прекрати содержательную работу и, если доступно, отключи автоматизацию. Если срок/слоты/неустранимые входные блокеры исчерпаны, опубликуй `<PARTIAL_FINAL_STATUS>` с полноценной проверенной выгрузкой, остатком, доказательствами и конкретными необходимыми входами; затем остановись. Не называй частичную готовность полной.

**Разрешённая для записи область:** `<RW_ROOT_URI>` и её явные дочерние каталоги `<DIAGNOSTICS_URI>`, `<CLAIMS_URI>`, `<CHECKPOINTS_URI>`. Все `<READ_ONLY_SOURCES>` доступны ТОЛЬКО ДЛЯ ЧТЕНИЯ; чужие файлы и старые checkpoint неизменяемы. Не создавай файлы в корне общего облачного диска. Не предполагается доступ к локальным дискам или физическим устройствам пользователя: никаких попыток монтирования, ожидания или обращения к ним. Используй только ресурсы, действительно предоставленные текущей сессии. Запрещённые средства: `<PROHIBITED_TOOLS>`.

### 2. Самое первое действие: диагностика и admission control

1. Зафиксируй UTC начало, monotonic start, `task_id`, уникальный `run_id`, номинальный slot, версию политики. Первым внешним шагом сделай ограниченное native-list разрешённого RW root и диагностической папки. НЕМЕДЛЕННО создай **новый** маленький `DIAG_<run_id>_S01_START.json`, получи metadata/readback при доступности. Не жди установки окружения и не загружай все ТЗ/ZIP до маркера старта.
2. Для задания, допускающего повторные/параллельные доставки, создай отдельную **immutable заявку** `CLAIM_<run_id>.json` в `<CLAIMS_URI>` с `task_id`, `run_id`, `nominal_slot`, `start_utc`, `parent_id`, `parent_sha_or_null`, `expires_at`. После загрузки прочитай серверное `created_time` из метаданных — не изобретай его внутри файла. Дважды native-list/readback всех недавних claims с коротким интервалом и оцени конкурентов. Внутри одного номинального слота приоритет у самой ранней серверной заявки; остальные **`DUPLICATE_SKIPPED`**. При недавнем незавершённом предшественнике **`ACTIVE_PREDECESSOR_SKIPPED`**. Неполный листинг, спорный slot, расхождение снимков, невозможность прочитать собственную заявку → **`LOCK_UNCERTAIN`** и прекращение содержательных записей.
3. Если бэкенд поддерживает **настоящую атомарную блокировку/CAS**, используй её и fencing token. Если доступны лишь Google Drive create/list/read, считай claim-арбитраж *кооперативным best-effort*, а НЕ гарантированным mutex. Даже при `LOCK_GRANTED` разрешены лишь независимые immutable stage/release; **не изменяй общие `CONTROL/LATEST`, ветку Git или другие общие pointers без атомарного CAS**. Непосредственно перед любым существенным изменением, финальным QA и публикацией заново проверь ownership, выбранный parent и отсутствие конкурирующего релиза. При сомнении — `FENCE_LOST`/`PARENT_CHANGED` и только уникальная изолированная WIP-ветка либо пропуск.
4. Любой отказ admission фиксируй в `S08_FINAL` с причиной и найденным competing run ID, заверши запуск без повторной предметной работы. Дубли — **штатный SKIP**, не предметный FAIL.

### 3. Preflight среды и входов

После подтверждения допустимости работы выполни **короткий** `S02_ENV`: фактически предоставленные текущему запуску файловую систему/права записи, Python/CLI, версии ОС, stdlib и **только требуемые этим WP** дополнительные модули, доступ к указанному облачному коннектору. `ENV_UNAVAILABLE` означает факт в этой сессии, а не необходимость ждать локальные диски пользователя. Не устанавливай необязательные зависимости. Если кодовая среда недоступна, но cloud reader работает, переключись на автономный source-review WP и явно отметь невозможность code/QA.

В `S03_SOURCES` native-list по ИМЕНИ: `CONTROL`, `LATEST`, `POLICY`, `HANDOFF`, `ISSUES`, `RUN_TIMINGS`, доступные PREQA/QA_STAGED/checkpoint/конкурирующие выпуски. Выбери **последний фактически существующий подходящий parent** с Drive/repo ID, SHA по реальным байтам, версией и допустимым статусом; старый `<INITIAL_CHECKPOINT>` — исключительно fallback, если более нового нет. Если контрольные файлы ещё не существуют в новом проекте — это `BOOTSTRAP`, а не fatal missing; инициализируй их только безопасным способом, не перезаписывая чужие. Используй актуальный HANDOFF и нужные разделы `<PRIMARY_SPEC_URI>`, а не пересчитывай всё исследование с нуля.

Исходные данные получать **лениво и адресно**, только для текущего пакета. Для отсутствующего/недоступного источника различай `SOURCE_UNREADABLE`, `SOURCE_MISSING`, `PERMISSION_DENIED`, `HASH_MISMATCH`, `UNVERIFIED_CANDIDATE`. Не объявляй missing, если source URL существует, но транспорт не прочёл байты. Хеши подтверждай только реально полученными байтами, не скопированным полем manifest. Повторы допускаются только при transient error, не более `<RETRY_N>` обращений/`<RETRY_SECONDS>` на ресурс; постоянные ошибки не ретраить.

### 4. Выбор содержательного чанка

Выбери **один** вертикальный work package (WP) или заранее ограниченное число независимых WP при доказанном резерве времени. Вертикальный означает: **входные данные → проверяемая трансформация/расследование → принятый содержательный результат → адресный QA → история/связи → HANDOFF**. Не подменяй его новым индексом, архивом, тестом, миграцией чужих строк или повторным чтением уже принятых материалов.

Приоритет выбирается по `<OBJECTIVE>`, `<BACKLOG>` и фактически закрытым P0, а не по красивому количеству выходных файлов. Продолжай внутри доступного бюджета после первого успеха, но **не начинай новый источник или новый WP после soft stop**. При заблокированном WP сохрани артефакт/причину и переключись на другой доступный небольшой WP, только если он успеет пройти gate и влезет в остаток времени.

Заранее зафиксируй три измеримых KPI с честными знаменателями и статусами, отдельно `INHERITED`, `NEW_DIRECT`, `PARTIAL`, `ACCEPTED`. После двух последовательных запусков без существенной принятой дельты переключись на `BLOCKER_TRIAGE`, измени стратегию, не прогоняй циклически те же тесты и не увеличивай случайно scope.

### 5. Время и раннее сохранение

Используй **измеряемый monotonic wall** с начала `S01`; не приписывай скриптовое или процессорное время всей сессии. Пока нет доказанного безопасного окна, предельный бюджет **24 минуты**, далее адаптация только по фактическим сериям запусков:

- 00:00–02:30 — S01, claim election, preflight, выбор parent.
- 02:30–12:30 — ровно один содержательный source-backed WP; **soft stop всех новых исходных правок на 12:30**.
- 12:30–15:30 — сохранить **immutable `PREQA_WIP`** с полной воспроизводимой дельтой, source manifest, checksum, HANDOFF; проверить remote readback.
- 15:30–20:00 — targeted QA, затем **одна** scoped regression на frozen inputs и чистой распаковке с явным source-root.
- 20:00–23:00 — `QA_PASSED_STAGED` cumulative или честный `WIP_ONLY`/`QA_FAILED`, upload, SHA/parent/readback, отчёт.
- 23:00–24:00 — финальный `S08_FINAL`; не начинай новый WP.

Если любая операция угрожает резерву QA/публикации, останови работу раньше и сохрани то, что уже воспроизводимо; весь невыполненный объём перенеси в HANDOFF. Если платформа прервёт сессию до `S08_FINAL`, нельзя из одного отсутствия маркера делать вывод о `PLATFORM_TIMEOUT`. Не обещай работу после закрытия текущего запуска; следующий запуск заново восстановит долговременный результат.

### 6. QA и выпуск

Перед тяжёлыми тестами обязательно опубликуй PREQA_WIP в постоянном хранилище. После этого **заморозь** код, входы, source hashes и schema версии. QA проводи: адресные проверки изменённого, один полный регрессионный gate необходимой области; негативные и boundary cases, SHA/CRC, соответствие источникам, parent lineage. Для исполняемого кода — тест через действительно доступный `sys.executable`, а не жёстко прописанный системный Python. Для расчётов — seed/precision/environment; для документов — целевые страницы/ссылки/формулы и целостность исходного текста.

**Clean restore обязателен:** распакуй в новый пустой каталог, извлеки source manifests и подготовь внешние READ-ONLY исходники в явном `<SOURCE_ROOT>`, проверь байтовые SHA, затем выполни указанные сборочные scripts и QA. Если внешний источник не удалось получить, итог `BLOCKED_SOURCE`/`SKIP_WITH_REASON`, но не `PASS_CLEAN_RESTORE`. Все использованные сборочные скрипты, тесты, параметризованные команды и lock/config должны находиться в checkpoint или быть адресуемы по immutable source reference. Не считай `N assert PASS` независимыми фактами предметной верификации.

Новый накопительный релиз **create-only/immutable**: сохраняет lineage, старые принятые поля, исходные версии; содержит новые данные/код/манифест/протокол QA, но **не дублирует большие неизменные RAW файлы, прошлые ZIP, картинки и колёса**, уже адресуемые по источникам. Проверяй ZIP CRC, внутренние SHA, внешний parent ID, размер и **скачанный обратно** SHA. Не перезаписывай общий pointer без CAS; при отсутствии CAS оставь `QA_PASSED_STAGED` и сообщение `PROMOTION_BLOCKED_NO_CAS`.

Если QA FAILED — не отменяй доказанные промежуточные результаты; опубликуй диагностические журналы, `QA_FAILED` и новый HANDOFF, но не меняй accepted KPI. Если upload не состоялся — `REMOTE_BLOCKED`, не утверждай, что временный файл является долговременным checkpoint.

### 7. Диагностика, отчёт и восстановление

Записывай **append-only маркеры** `S01_START`, `S02_ENV`, `S03_SOURCES`, `S04_WORK`, `S05_PREQA_WIP`, `S06_QA`, `S07_PUBLISH`, `S08_FINAL`, а при перехватываемой ошибке `SXX_ERROR`. Каждый маркер содержит UTC, run/slot/task IDs, stage, статус, monotonic elapsed, parent/source IDs+SHA, результаты fence, before→after KPI, точные команды и их exit code/duration/stdout/stderr (коротко и без секретов), retries/latency, реальные созданные remote IDs. Нет этапа — не симулируй маркер. Не записывай токены, заголовки авторизации, подписанные download URLs и приватные абсолютные пути пользователя.

В конце отправь краткий содержательный **русский** отчёт: `RUN` и номинальный slot; режим (`DEVELOPMENT`, `RECOVERY`, `QA_ONLY`, `PUBLISH_ONLY`, `FINALIZE`, `DUPLICATE_SKIPPED`); 1–3 завершённых вертикальных результата; **три KPI before→after**; фактический wall и фазовые timings; QA с PASS/FAIL/SKIP/TIMEOUT; Drive/repo URLs, реальные SHA+parent+readback; открытые P0; точный следующий WP. Если заданию нечего делать или до первого внешнего вызова всё упало — честно укажи отсутствие доказательств, а не фиктивный SUCCESS.

**Порядок восстановления следующего часа:** remote list/claims/terminal markers → самый свежий verified/staged checkpoint → незавершённые WIP → нужные первичные байты → `RECOVERY` или `QA_ONLY` вместо механического нового исследования. Никогда не откатывайся к статическому стартовому URL, если есть поздний доказанный релиз.

## C. Протокол поведения, когда автоматизация нестабильна

### C1. Почему нельзя начинать с чтения всех ТЗ и установки зависимостей

Первая доступная внешняя операция может упасть до появления отчёта. Поэтому минимальный trace `S01_START` сохраняется **до** чтения десятков документов, ZIP или установки инструментов. Если отказ произошёл ещё до первого успешного облачного вызова, облачного лога не будет: это диагностическая граница, а не доказательство ошибки пользовательских файлов. Важна *готовность* среды, а не ожидание её установки. Локальные диски пользователя существуют отдельно от облачной сессии и не должны проверяться без явного подключения.

### C2. Кооперативная защита и настоящий lock — разные вещи

| Сервис / операция | Гарантия |
|---|---|
| Новый файл `CLAIM_<run_id>.json` + два list/readback + сортировка server timestamp | Практическое снижение риска дублей; **не атомарный mutex** |
| Только уникальные WIP/QA_STAGED с parent SHA; запрет общих перезаписей | Сохраняет данные даже при гонке; может потребовать последующего merge |
| Atomic compare-and-swap / транзакция / lease с fencing token у внешнего координатора | Строгая блокировка **только если семантика действительно подтверждена и правильно реализована** |
| Совпадение имени `LOCK.json` в Google Drive | **Не является блокировкой**: два писателя могут создать два файла |

Если источники утверждают, что list полный, но бэкенд не гарантирует consistency/atomicity, обозначай `COOPERATIVE_CLAIM`, не `GLOBAL_LOCK_ACQUIRED`. Если поздно пришедший претендент ещё не виден, абсолютной эксклюзивности нет; поэтому нельзя мутировать общую каноническую запись. TTL не означает, что старый процесс погиб: после истечения TTL и отсутствия терминального маркера статус `STALE_UNCONFIRMED`, требуется проверка новых WIP/публикаций, parent и, при необходимости, только staging.

### C3. Размер чанка подстраивается под измерения

| Режим | Когда применять | Wall ceiling | Предметная фаза | Выпуск |
|---|---|---:|---:|---|
| **Conservative (по умолчанию)** | Были неясные обрывы, плавающее время или новая среда | 24 мин | До 12,5 мин, один WP | WIP + scoped QA + staged |
| **Micro-recovery** | Исходники частично недоступны, WIP нужно спасти, конкуренция | 8–12 мин | Только восстановления/QA/публикации | Сохранённый результат без нового WP |
| **Expanded (по данным, не по желанию)** | После нескольких последовательных RUN с `S08_FINAL`, запасом времени и без внешних обрывов | Например, 30–40 мин, если реально достижимо | 1–3 WP с ранним WIP | Не жертвовать QA и readback |

Не повышать `wall ceiling`, пока не подтверждены устойчивые завершения. Режимы не изменяют частоту запуска; они управляют **внутренним** бюджетом. Если QA завершается за секунды до soft-stop, используй оставшуюся часть предметной фазы; если soft-stop уже прошёл — не размораживай inputs ради ещё одной карты/коммита. При большом массиве источников делай ленивый source hydration и отдельные проверяемые чанки, а не повторный полный download каждый час.

### C4. Диагностика по последнему маркеру

| Наблюдение | Что установлено | Чего утверждать нельзя | Следующее действие |
|---|---|---|---|
| У планировщика есть run, но нет S01 | Нет доказательства первого успешного Drive write | «Не запускалось» или «точно timeout» | Проверить подключение/доступ к инструментам; при повторении — поддержка платформы |
| S01 есть, claim нет | Успешное первое облачное сохранение | Причину обрыва | Проверить ошибку claim-upload и права на дочернюю папку |
| Есть claim, нет `LOCK_GRANTED` | Арбитраж не завершён | Что работает единственный writer | Проверить двухкратный листинг, слоты, терминальные маркеры |
| `DUPLICATE_SKIPPED` в S08 | Второй запуск обнаружил конкурента и штатно вышел | Что основной запуск непременно закончил работу | Смотреть главный run по ID |
| S02 есть, S03 нет | Среда/короткий preflight прошли | Что источники пропали | Проверить конкретный fetch/HANDOFF |
| S04 есть, S05 нет | Предметная работа началась/что-то произведено | Что данные сохранились | Восстанавливать только из durable WIP/исходников |
| S05 есть, S06 нет | WIP опубликован | Что QA прошёл | Следующий цикл = `QA_ONLY` |
| S06 есть, S07 нет | QA завершён в измеренной области | Что архив опубликован | `PUBLISH_ONLY`, verify frozen input |
| S07 есть, S08 нет | Архив опубликован (если есть readback) | Что всё штатно завершилось | Проверить hash/parent; оформить HANDOFF |
| `TIME_BUDGET_REACHED` в S08 | Запуск сам ограничил время | Что это лимит OpenAI | Сравнивать с реальными фазовыми временами |
| Нет маркера после определённой минуты | Последняя доказанная стадия | Что обязательно сработал platform kill | Проверить позднее; без traceback оставить `INTERRUPTION_CAUSE_UNKNOWN` |

### C5. Классификация завершения запуска и релиза

**Run-level terminal statuses:** `SUCCESS`, `WIP_ONLY`, `QA_FAILED`, `DUPLICATE_SKIPPED`, `ACTIVE_PREDECESSOR_SKIPPED`, `LOCK_UNCERTAIN`, `FENCE_LOST`, `SOURCE_BLOCKED`, `ENV_UNAVAILABLE`, `REMOTE_BLOCKED`, `TIME_BUDGET_REACHED`, `ERROR`, `INTERRUPTION_CAUSE_UNKNOWN` (последний проставляется в аналитике следующего запуска, не «самостоятельно» погибшим процессом).

**Artifact-level states (независимы от run):** `CANDIDATE` → `UNVERIFIED_WIP` → `QA_PENDING` / `QA_FAILED` → `QA_PASSED_STAGED` → `PROMOTED` (только после всех обязательных проверок и безопасного обновления канона). `COMPLETE` и `PARTIAL_FINAL_BLOCKED` относятся к **проекту целиком**. Число ZIP, тестов, локальных asserts и входных записей не является доказательством достигнутого KPI.

**Источник ≠ утверждение ≠ факт:** хранить раздельно `SOURCE_PRESENT`, `SOURCE_HASH_VERIFIED`, `FIELD_DIRECT_VERIFIED`, `SEMANTIC_ACCEPTED`, `RULE_EFFECTIVE_VERIFIED` и `TEMPORAL_APPLICABILITY_VERIFIED`, если применимо. Запрещено использовать одно обобщающее поле `verified=true` для всех уровней.

## E. Acceptance tests именно для автоматизации (не для предметной БЗ)

Проверять отдельно от тестов проекта. Для новой задачи сначала **dry-run вне расписания** без вмешательства в канон; затем анализ первых штатных циклов.

- [ ] `S01_START` опубликован ДО fetch большого документа или установки модулей.
- [ ] В новом сеансе реально прочитаны/записаны только разрешённые объекты; исходные папки остались RO; в My Drive root не появилось собственных файлов.
- [ ] Работает сценарий **два претендента одного слота**: единственный выбранный кандидат, другой `DUPLICATE_SKIPPED`, без новой предметной записи.
- [ ] Работает сценарий **незавершённый предшественник другого слота**: `ACTIVE_PREDECESSOR_SKIPPED`/fail closed, без блокирующего ожидания.
- [ ] Ошибки incomplete list, неподтверждённый source hash и изменившийся parent переводят в `LOCK_UNCERTAIN`/`BLOCKED_SOURCE`/`PARENT_CHANGED`, а не в принудительный PASS.
- [ ] При имитации сбоя после `S05_PREQA_WIP` следующая сессия возобновляет `QA_ONLY`, не повторяет весь предыдущий WP.
- [ ] Принятые данные воспроизводятся из **чисто распакованной** версии с manifest и отдельным явным source-root.
- [ ] При попытке обновления `CONTROL/LATEST` без CAS происходит отказ; архив остаётся `QA_PASSED_STAGED`.
- [ ] В `RUN_TIMINGS` реальный `run_wall`, а не `script_wall` или суммарные CPU-секунды; отсутствующий финальный маркер не маркируется автоматически `PLATFORM_TIMEOUT`.
- [ ] После достижения `COMPLETE` или лимита N/даты следующий вызов не открывает новые WP; конечный отчёт/выгрузка доступны.

**Оценка эффективности:** считать не количество уведомлений, токенов и ZIP, а `accepted_delta / календарный час`, `доля слотов с S08`, `доля выпусков с raw readback`, `число потерянных WIP`, `число конкурирующих публикаций`, `время от первичного источника до принятого результата`, `число необъяснённых обрывов`.

### Что является предложенной инженерной политикой, а не доказанным свойством платформы

1. **24-минутный self-limit** — консервативное решение на основании наших журналов, а **не официальный timeout OpenAI**. Внешняя граница исполнения и причины server-side обрыва могут меняться и не видны без логов платформы.
2. **Claim election на Drive** — эмпирически проверенный механизм пропуска конкретного дубля, **не строго линейризуемая распределённая блокировка**. Не гарантирует единственного writer при невидимых одновременно созданных файлах.
3. **Два списка с паузой 3–5 секунд и TTL 33 минуты** — эвристические параметры; не гарантируют консистентность или гибель старого процесса. На новом бэкенде подбирать параметры по его документированным гарантиям.
4. **6–10 карт, 12–25 правил, один WP за цикл** — пример sizing Conquest; у другого проекта будут другие единицы прогресса и другая фактическая пропускная способность.
5. **Сохранение на облако из Scheduled Task** работает только после успешной инициализации подключённого инструмента и разрешённых операций. Если инструмент отсутствует или сеанс прерывается до первой записи, «лог на облаке» не может возникнуть автоматически.

## G. Практическая настройка расписания

Для фиксированного числа почасовых **номинальных** слотов пример iCalendar (подставить будущее UTC и своё количество):

```ical
BEGIN:VEVENT
DTSTART:20261101T090000Z
RRULE:FREQ=HOURLY;COUNT=48
END:VEVENT
```

Для конечной календарной даты без числа итераций можно использовать корректный `UNTIL` (без одновременного `COUNT`), а внутри каждого запуска независимо соблюдать project hard limit. **Не продлевать** `COUNT/UNTIL` при ошибках или SKIP без явного решения пользователя. Предпочтительно запускать с запасом от текущего времени; не назначать `DTSTART` в прошлое на секунду, чтобы избежать неопределённости первой доставки. Часовой cadence означает *возможность очередного запуска*, а не гарантию длительного непрерывного процесса или единственной доставки.

**Правило масштабирования:** сначала добиться регулярного `S08_FINAL` в 24-минутном режиме. Только после ≥3 последовательных полных запусков с измеренным безопасным запасом можно *рассматривать* более длинный лимит, не меняя частоту и без гарантий, что платформа даст такую длительность. Если новых S08 нет, сначала локализовать обрыв и уменьшить пакет, а не усложнять расписание.

## H. Быстрая адаптация вертикального WP к разным типам задач

| Направление | Единица **содержательной** дельты | Source of truth | Примеры нужного QA | Что не считать прогрессом |
|---|---|---|---|---|
| Исследовательская БЗ | Полностью проверенный объект/поле, атом нормы, снятый конфликт с доказательством | Первичный документ, изображение, аудио/видео с локатором и SHA | Непосредственная сверка оригинала, typed constraints, lineage, coverage denominator | OCR-кандидат, индекс URL, импорт старых строк |
| Разработка и рефакторинг | Закрытый сквозной контракт/удалённый дубликат, реальный diff с acceptance | Frozen Git commit, lockfile, тестовый оракул | Unit/integration/behavioral regression, clean env, exact input | Количество новых классов, заглушек, тестов без исправленного поведения |
| Научные расчёты | Воспроизведённый эксперимент/гипотеза с численным результатом, неопределённостью и параметрами | Сырые данные, модель, equations, seeds, версии библиотек | Re-run, convergence, invariants, численная устойчивость, sensitivity | Количество графиков, запусков без валидной физической интерпретации |
| Документы/монография | Завершённая содержательная секция с точными ссылками и проверенной типографикой | Замороженный source master и первичные публикации | Сборка, ссылки, уравнения, визуальная проверка изменённых страниц | Новое PDF без новой доказательной или редакторской ценности |
| ETL/таблицы | Проверенная бизнес-трансформация, покрытие строк и schema/constraints | Неизменяемый вход + spec/schema + expected outputs | Deterministic replay, row counts, schema, reconciliation, fixtures | Просто больше строк или дополнительных столбцов |
| OSINT/внешние источники | Новый уникальный извлечённый источник или доказанный negative acquisition | URL/ID, дата, bytes, authority, content hash | Deduplication, provenance, anti-staleness, explicit failed attempts | Повторная попытка к тем же битым URL без новых условий |

**Для вычислительно долгих работ:** вместо одного непрерываемого тяжёлого subprocess использовать *идемпотентные чанки* с входным manifest, однозначными seed/range, hash результатов и per-chunk statuses. В каждый час запускается только доступная порция, а полный агрегационный gate проводится после завершения всех обязательных чанков. Не увеличивать число запусков в расписании ради незавершённого расчёта.

### Краткая формула исполнения

**Установить границы → сохранить `S01` → согласовать writer → восстановить новейший parent → один source-first WP → ранний immutable WIP → чистый QA → remote hash/readback → `S08_FINAL` + HANDOFF → следующий час продолжает без повтора → конечный COMPLETE или PARTIAL_FINAL_BLOCKED.**
