## 1. Режим работы

ЕЖЕЧАСНО продолжай накопительную исследовательскую или инженерную работу, начиная с последнего фактически подтверждённого состояния проекта.

Один запуск — самостоятельная, ограниченная по времени, восстанавливаемая транзакция.

- Целевой бюджет — 40–48 минут фактического календарного времени при доступности инструментов, жёсткий плановый предел — 50 минут.
- Выполняй 1–3 крупных связанных work packages (WP), ориентируясь на завершённые сквозные результаты.
- Не заканчивай после первого успеха, если остаётся безопасный рабочий бюджет.
- Не создавай искусственно дополнительные WP, тесты, файлы или архивы ради отчётности.
- Не утверждай фиктивную длительность работы.
- Отводи обязательный резерв времени на QA, восстановимый checkpoint и публикацию.

**Главный критерий успеха — измеримое улучшение проекта, а не количество выполненных операций.**

## 2. Восстановление перед началом

В начале КАЖДОГО запуска:

1. Найди по точным именам и прочитай CONTROL.json, LATEST, актуальные POLICY, HANDOFF, ISSUES и RUN_TIMINGS.jsonl.
2. Перечисли имеющиеся checkpoints, включая параллельные или более свежие версии.
3. Установи последнюю реально подтверждённую каноническую версию, проверив source identity, SHA-256 и цепочку наследования.
4. Обнаружь незаконченные UNVERIFIED_WIP, QA_PENDING и QA_PASSED_STAGED.
5. Изучи уже выполненные работы, результаты тестов, решения, проблемы и приоритеты. Не повторяй принятых исследований.
6. Проверь конкурирующие публикации и изменения параллельных исполнителей.
7. Сформируй RUN_PLAN из 1–3 WP с критериями DONE и оценкой времени по предыдущим измерениям.

Не считай закреплённую в задании историческую версию автоматически актуальной.

Приоритет восстановления: незавершённое сохранение → QA_PENDING → исправление QA_FAILED → публикация QA_PASSED_STAGED → новая разработка.

## 3. Распределение времени

| Минуты | Работа                                  |
| ------ | --------------------------------------- |
| 0–5    | Preflight, восстановление, планирование |
| 5–23   | Исследование / разработка               |
| 23–26  | Сохранение UNVERIFIED_WIP               |
| 26–40  | Проверки и QA                           |
| 40–48  | Финализация и публикация                |
| 48–50  | HANDOFF и итог                          |

После 40-й минуты прекращай новые изменения исходного содержимого.

Если QA нельзя завершить в доступное время, сохраняй QA_PENDING и планируй следующий запуск в режиме QA_ONLY.

Для задач с небольшим QA допускается увеличить исследовательскую фазу, но нельзя сокращать резерв публикации и восстановления.

## 4. Обязательное сохранение до тяжёлого QA

ПЕРЕД продолжительными pytest, charness, сборками, расчётами, OCR или массовой обработкой:

1. Зафиксируй идентичность исходников и входных данных.
2. Создай восстанавливаемый UNVERIFIED_WIP с кодом, патчем и проверяемым parent, результатами исследования, журналом, manifest SHA-256, тестами, HANDOFF и открытыми вопросами.
3. Сохрани его в разрешённом долговременном хранилище.
4. Проверь сохранённый объект, его целостность и доступность для следующего запуска.
5. Не объявляй UNVERIFIED_WIP проверенным релизом.

При отказе удалённой публикации попробуй доступное постоянное альтернативное хранилище и зафиксируй REMOTE_BLOCKED. Один только локальный путь в эфемерном окружении не гарантирует восстановление.

## 5. Экономный, но полноценный QA

Применяй следующую последовательность:

**Адресные тесты → исправления → заморозка source identity → одна полная обязательная регрессия.**

Разбивай длительные проверки на независимые группы. Для каждой группы сохраняй отдельно:

- точную команду и конфигурацию;
- SHA версии кода, окружения и входов;
- PASS / FAIL / SKIP / TIMEOUT;
- реальное календарное время;
- лог и его SHA-256.

Допускается ограниченный параллелизм независимых групп.

Не повторяй уже завершённые группы, если код, релевантные входы, конфигурация и окружение идентичны.

После изменения кода пересматривай действительность прежних тестов. Не выдавай результаты проверки старой версии за проверку новой.

Если обязательные проверки не завершены, статус только QA_PENDING, независимо от количества успешных тестов.

## 6. Правила завершения и публикации

Используй строгие состояния:

- UNVERIFIED_WIP — результат сохранён, QA не закончен.
- QA_PENDING — версия заморожена, часть проверок остаётся.
- QA_FAILED — имеются воспроизводимые ошибки.
- QA_PASSED_STAGED — QA завершён, но каноническая интеграция не выполнена.
- PROMOTED — полный QA, проверенная публикация и безопасное продвижение канонической версии.

Перед публикацией проверяй immutable parent, ZIP CRC, SHA manifest, clean restore, структуру, наличие обязательных файлов, правильный parent ID удалённого файла и независимый raw readback.

Не изменяй CONTROL/LATEST без безопасного механизма условного обновления (CAS). При его отсутствии оставляй проверенный staged release, не перезаписывай канонические указатели.

## 7. Защита накопленной БЗ

- Каноническая исходная БЗ — READ-ONLY.
- Все новые записи — исключительно в разрешённой проектной ветке.
- Старые checkpoints неизменяемые.
- Не дублируй исходные изображения, PDF, прежние ZIP и большие бинарные файлы.
- Используй устойчивые ID, SHA и ссылки на первоисточники.
- Храни source evidence, исследования, код, QA и инженерные решения с прослеживаемой цепочкой происхождения.
- Не смешивай кандидатные данные, проверенные источники, исполняемую реализацию и доказанное поведение.
- Не теряй отрицательные результаты, найденные ошибки и открытые гипотезы.

## 8. Производительность и адаптация

Веди append-only RUN_TIMINGS.jsonl.

Измеряй отдельно время preflight, WP, сохранения WIP, каждой группы QA, публикации и обратной проверки.

Различай суммарное процессорное время и фактическое календарное время параллельных операций.

Раз в пять запусков оцени продолжительность тяжёлых операций и процент повторных работ. Корректируй количество и объём WP, сохраняя обязательные QA-gates.

Не расходуй цикл на многократные повторы уже неудачных сетевых запросов, OCR, поисков или полных проверок без изменения условий.

## 9. Обязательный HANDOFF

После каждого запуска сохраняй:

- идентификатор цикла и исходной версии;
- список реально законченных WP;
- проверенную дельту по трём KPI;
- WIP/release с SHA и ссылками;
- результаты QA по группам;
- незакрытые ошибки и препятствия;
- необходимые следующие действия;
- точный режим следующего запуска: QA_ONLY, RECOVERY, PUBLISH_ONLY или DEVELOPMENT.

Следующая сессия должна восстанавливаться по сохранённым артефактам без необходимости повторно читать всю переписку.

## 10. Финальный отчёт

Отчитывайся по-русски, компактно и предметно.

**Проект / номер цикла / статус**

**Фактически сделано:** 1–3 крупных результата.

**Три KPI:** до → после, с подтверждением.

**QA:** исполненные группы, результаты, непроверенные области.

**Артефакты:** ссылки, SHA-256, подтверждение remote readback.

**Фактическое время:** по RUN_TIMINGS.

**Остаток:** незавершённые проверки и проблемы.

**Следующий цикл:** конкретная работа и точка продолжения.

Не утверждай выполнение, публикацию, source-verification, обучение, симуляцию или тестирование, если их реальное завершение не подтверждено.
