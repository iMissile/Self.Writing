# Вычислительный сервер

Используйте этот skill для работы с серверным запуском и результатами вычислительных заданий. Научную постановку, физические параметры и критерии анализа определяет пользователь.
Исходное описание tools не подтверждает production-доступность: используйте только операции, реально подключённые в текущем сеансе.

Установку portable client, локальную конфигурацию stdio MCP и отдельное управление scoped API-ключами выполняйте по [инструкции платформы](references/platform-setup.md).

## Подготовка и подача

На текущем узле разрешены до трёх независимых Wolfram kernel и до трёх Python-заданий, но общая ёмкость пула — три задания суммарно. Каждое задание получает один CPU; суммарный бюджет памяти пула — 5 GiB. Перед каждой подачей проверяйте актуальный `compute_capacity` для точного deployment и используйте только атомарный `compute_try_submit`. Три Wolfram-задания с лимитом 1.5 GiB каждое помещаются по памяти; три задания по 2 GiB — нет. Указывайте лимит по измерениям задачи, а не копируйте пример молча. Не вызывайте дополнительные `LaunchKernels[]` внутри таких заданий без отдельного согласования ресурсного и лицензионного бюджета.

- Для автономной подготовки deployment используйте распакованный каталог `client/` из `wolfram-platform-client.zip` как SDK root. Запускайте его CLI только через `uv`: `uv run --offline --locked --no-sync --project <client> python <client>/scripts/compute-client.py --request-id <stable-id> prepare --spec <spec.json> --output <new-bundle-dir>`.
- В `spec.json` задайте `roots.client` равным абсолютному каталогу `<client>`. В `files` сопоставьте пакетные пути с файлами SDK: для Python добавьте `runners/python/closed_block.py` как `runner`, `science/task.py` как `source`, `sdk/compute_client/{__init__.py,common.py,checkpoint.py,runner.py}` и `sdk/wolfram_telemetry/{__init__.py,writer.py,reader.py,exports.py,schema.py,event.schema.json}` как `instrumentation`; для Wolfram используйте `runners/wolfram/ClosedBlockRunner.wl` как `runner`, `science/task.wl` как `source`, `sdk/compute_client/{__init__.py,common.py,checkpoint.py}` и `runners/wolfram/RunTelemetry.wl` как `instrumentation`. В обоих профилях добавьте `config/config.json` с ролью `config`, а полный совместимый `pyproject.toml` и соответствующий `uv.lock` с ролями `environment` и `lock`. Для синтетического smoke без дополнительных библиотек можно взять `<client>/pyproject.toml` и `<client>/uv.lock`; для научной задачи явно включите требуемые ей зависимости и передайте собственные проверенные environment-файлы. Заполните все обязательные поля `contract` по схеме `compute_client.bundle.build`.
- Сверяйте source/config/instrumentation и environment SHA по manifest; для изменённого snapshot требуются причина и точное состояние дерева. Клиентский пакет содержит только общие runner и инструментацию: `science/task.py` или `science/task.wl`, конфигурацию, входные данные и параметры ресурсного контракта предоставляйте явно для каждой задачи.
- На узле `wolfram-server.ru` 28.10.2026 входной бюджет повышен до 1 ГиБ (1 073 741 824 байта): весь compute bundle, сумма распакованных файлов, отдельный файл и источник datasets. Перед передачей прочтите текущие capabilities: это датированный снимок, не неизменяемая константа протокола. В ZIP-бюджет входят код, все inputs и служебные байты; файл ровно 1 ГиБ вместе с обвязкой в такой bundle не помещается. Клиентские transfer budgets также задавайте явно. Размер WXF на диске не определяет RAM после `Import`; память выбирайте по измерению задачи. Изменение лимита не является приёмкой реальной передачи или вычисления на 0,8 ГБ.
- Перед каждой новой задачей подготовьте корневой `job-card.md` на русском языке: UTF-8, Markdown, не более 65 536 байт. В `files` добавьте его как `{ "root": "...", "path": "job-card.md", "role": "config" }`; он входит в immutable manifest с точными `bytes` и SHA-256.
- Карточка должна содержать H1-заголовок и ровно эти обязательные H2-разделы: `Цель`, `Входные данные`, `Модель и формулы`, `Метод расчёта`, `Выходные данные`, `Ограничения и критерии`, `Воспроизводимость`. В разделе модели укажите цель и физический смысл, уравнения, обозначения, единицы и допущения; в методе — алгоритм, численную точность и устойчивость; во входных данных — происхождение и SHA-256; в воспроизводимости — исходники, упорядоченные блоки, ресурсы и ETA либо причину, по которой она неизвестна. Укажите ожидаемые outputs и проверяемые критерии.
- Используйте только постановку, формулы, данные и критерии, заданные владельцем. Не выводите физику из имени проекта, кода или результатов. Если задача общая или IT, явно напишите `Не применимо` и почему для физического смысла/модели; не придумывайте уравнения. Недостающие научные определения отметьте как не заданные и запросите их до подачи. Формулы записывайте стандартной LaTeX-разметкой Markdown (`$...$`, `$$...$$`), сохраняя определения символов и единиц.
- Подбирайте содержательные блоки до подачи: делите только по математически независимым единицам (например, параметрической сетке, независимым реализациям или независимым областям), когда агрегация сохраняет исходный метод, порядок/seed и provenance. Размер блока выбирайте по измеренному pilot с учётом стоимости запуска, checkpoint, передачи данных, восстановления и стоимости pause/cancel; не дробите работу на RPC-задачи по 5 секунд и не задавайте научную длительность по умолчанию. Длительная задача может выполняться часами на сервере и не зависит от времени жизни агента или открытого клиентского соединения; закрытие transport не отменяет job.
- Подайте задание один раз со стабильным `request_id`, затем при необходимости выполняйте ограниченный polling. Повтор запроса сохраняет тот же ID; не запускайте второе задание из-за окончания сеанса агента. Прогресс подтверждается только проверенными closed-block checkpoints. Текущий in-block phase/heartbeat telemetry описывает работу внутри блока, но не означает завершённый блок или запись результата.
- Карточка фиксирует план блоков, число записей, измеренную оценку времени либо причину `неизвестно`, ресурсы CPU/памяти, зависимости между блоками, immutable inputs, метод и точность/допуски. Не выбирайте научный шаг, tolerance или seed самостоятельно.
- Поддерживаемый Python-адаптер вызывает `science.compute_block(config, block)`; блок считается завершённым только после записи и проверки checkpoint `closed-block-v1`. Указывайте ожидаемое число записей, резерв свободного места и лимит памяти из явного контракта пакета.
- Для `wolfram_closed_block_v1` файл `science/task.wl` определяет `QWComputeBlock[config_Association, block_Association]`: это точка входа адаптера существующих научных функций в том же kernel. Полные объекты сохраняются в declared native-файлы, возвращаются небольшие Associations для checkpoint. Допустим один длительный блок на весь неделимый расчёт; при потере процесса незакрытый блок выполняется заново целиком. В одном job блоки последовательны; три параллельных kernel означают независимые jobs общего пула. Контракт и схема обёртки приведены в [инструкции native-результатов](references/native-artifacts.md#адаптер-wolfram-и-длительный-блок). Наличие платформенного smoke не доказывает совместимость конкретного скрипта: проверяйте пути, `Exit[]`, очистку контекста, зависимости и controlled Import/научную QA отдельно.
- `capabilities` и `capacity` дают наблюдение для планирования. Для native задания используйте `compute_try_submit_typed` с явным `result_formats`, равным набору форматов required outputs immutable deployment. Это проверка контракта до admission, а не автоматическая конвертация. Совместимый `compute_try_submit` сохраняется для v1. В обоих случаях `busy` означает, что задание не принято; не создавайте скрытую локальную очередь и не повторяйте попытку по кругу.
- Перед новой группой задач прочтите `compute_resources` с окнами `windows_seconds: [30, 300]`. API допускает от одного до четырёх уникальных окон в пределах настроенного `history_seconds`; `[30, 300]` — текущие значения по умолчанию, не гарантия наличия полной истории. Для хоста и каждого worker сверяйте current/peak, mean, median, variance (`ddof=0` для всей наблюдённой совокупности), coverage и gaps. Mean, median и variance взвешены длительностью наблюдаемых интервалов. История описывает логический worker и может продолжаться между заданиями; смена identity/attempt образует неизвестную границу и пробел, а не нулевое потребление. Не трактуйте пропуск, stale или unknown как ноль. Решение о приёме учитывает текущие ресурсы и живые брони; 5-минутное среднее само по себе не разрешает запуск. При `busy`/stale/недостаточной истории не увеличивайте число kernels и не обходите admission через SSH.
- Точные MCP имена compute: read-only `compute_capacity`, `compute_resources`, `compute_status`, `compute_job_card`, `compute_artifacts`, `compute_artifact_manifest`, `compute_list_jobs`; подача `compute_try_submit`, `compute_try_submit_typed`; изменяющие операции `compute_control`, `compute_approve`.
- Если установлен CLI, выясняйте его актуальный invocation через `--help`; не выводите флаги из этого skill и не используйте неподтверждённый интерфейс. Запускайте Python-клиент только через `uv`.
- При повторе той же операции используйте тот же `--request-id`; новая операция получает новый ID. В `approve` передавайте точный manifest SHA, evidence SHA и обоснование только при явном полномочии на утверждение.
- При `Transport closed` сначала восстановите transport, выполните `initialize`, `tools/list` и свежий read-only запрос. Обрыв не доказывает, что серверная подача не состоялась: сверяйте `compute_list_jobs`/`compute_status`, не создавайте новое задание и не меняйте `request_id` для повтора той же подачи. Не автоматизируйте UI MCP-клиента.

## Повторы и результат

- Автоматическое восстановление предусмотрено только для `worker_lost`, максимум три раза и только с проверенным checkpoint. Другие ошибки не запускайте повторно автоматически.
- Читайте состояние через API/MCP. ETA называйте только если API подтвердил её по сопоставимому wall-time текущей попытки; иначе сообщайте «неизвестно». Не подменяйте wall-time CPU-временем.
- Артефакт считайте опубликованным после проверки allowlist, размера и SHA. Восстановление данных не объявляйте готовым по одному совпавшему SHA: нужен проверенный application-level read/restore.

## Учётные данные и границы полномочий

- Передавайте только путь к закрытому credential-файлу; токен читает процесс клиента. Не открывайте и не копируйте секрет в контекст, аргументы команд, stdout, stderr или commit.
- Не переходите к root/SSH и не меняйте чужую задачу. Если пользователь поручил подготовить и запустить вычисление, а текущая роль/scopes разрешают approve, утвердите только проверенные manifest SHA и evidence SHA с обоснованием в рамках этого поручения — дополнительное подтверждение не требуется. Если нет роли admin или `compute:approve`, передайте готовый пакет и evidence уполномоченному оператору.
- `pause`, `cancel` и `resume` требуют явного запроса пользователя; для `resume` передайте API требуемое подтверждение `approve`.

## Полные результаты WXF и Parquet

Для больших нативных трасс и обязательных файлов изучите [контракт native-artifacts-v1](references/native-artifacts.md). Не подменяйте полный WXF табличным сокращением. Все объявленные required файлы публикуются до checkpoint; большие binary скачиваются отдельным HTTP/SDK-процессом с явным форматом, возобновлением и конечной проверкой SHA.
