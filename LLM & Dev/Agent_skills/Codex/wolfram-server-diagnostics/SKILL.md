# Диагностика сервера

Начинайте с read-only API/MCP состояния. Не меняйте сервисы, очередь или задание ради диагностики.
Используйте только реально подключённые read-only операции; наличие route в source не подтверждает production rollout.

## Read-only каналы

- Для datasets readiness доступен `GET /health/ready`; он показывает готовность сервиса, а не результат конкретного задания.
- Read-only MCP names для compute: `compute_capacity`, `compute_resources`, `compute_status`, `compute_job_card`, `compute_artifacts`, `compute_artifact_manifest`, `compute_list_jobs`. `compute_control`, `compute_try_submit`, `compute_try_submit_typed` и `compute_approve` не являются read-only операциями.
- Read-only MCP names для datasets: v1 `datasets_list`, `datasets_get`, `datasets_metadata`, `datasets_schema`, `datasets_preview`; v2 `datasets_v2_capabilities`, `datasets_v2_list`, `datasets_v2_metadata`, `datasets_v2_manifest`, `datasets_v2_schema`, `datasets_v2_preview`. Сверяйте доступные инструменты через `tools/list` в каждом подключении.
- `compute_resources` по умолчанию использует окна `windows_seconds: [30, 300]`. Mean, median и variance (`ddof=0` для всей наблюдённой совокупности) взвешены длительностью фактических интервалов. Проверяйте current/peak, coverage, gaps и status у хоста и каждого worker. История относится к логическому worker и может пересекать задания; смена identity/attempt — неизвестная граница, которая видна как пробел. Не трактуйте unknown, stale или gap как нулевую загрузку.
- Если установлен CLI, используйте только действия, показанные его `--help`; не придумывайте команды чтения журналов. Для trace выбирайте поддерживаемый формат Perfetto или Speedscope. `fetch` — локальная запись разрешённого артефакта, не read-only для файловой системы; сверяйте allowlist, размер и SHA.
- Если нужен raw service log, используйте только уже настроенный read-only diagnostic channel. Не выдумывайте `logs` CLI и не переходите к root/SSH или чтению секретной конфигурации.

## Прогресс и восстановление

- Серверная задача может длиться часами и продолжает выполняться при закрытии клиентского соединения или завершении агентского сеанса. Сначала продолжайте наблюдение той же задачи; не создавайте RPC-задачи-«микропробы» по 5 секунд и не запускайте замену только потому, что наблюдатель отключился.
- При `Transport closed` восстановите transport вручную, выполните `initialize`, `tools/list` и свежий read-only probe. Не автоматизируйте UI клиента. Неизвестный ответ на подачу не означает отказ: сначала найдите задание через `compute_list_jobs`/`compute_status`, не создавайте дубликат; повтор той же подачи использует прежний `request_id`.
- Статус и in-block telemetry отражают разные факты: живой heartbeat или завершённая фаза внутри блока не равны закрытому результату. Подтверждайте прогресс только SHA-проверенными checkpoints завершённых блоков.

- Worker/job идентифицируйте именами и ресурсами из API. Не выводите их из OS thread IDs, PID или количества системных потоков.
- ETA считайте достоверной только при проверенном checkpoint и telemetry сопоставимой текущей попытки. Источник — wall-time; CPU-time не подменяет wall-time. При неполных данных возвращайте «неизвестно» и причину.
- Статус `running` сам по себе не доказывает продвижение. Сверяйте завершённые записи с SHA-проверенными блоками checkpoint и событиями текущей попытки.
- Не перезапускайте научную работу для получения более удобного отчёта. Автоматический retry ограничен `worker_lost` и проверенным `closed-block-v1` checkpoint; прочие сбои требуют решения владельца.
- `pause`, `cancel` и `resume` меняют состояние и требуют явного запроса пользователя. `resume` требует явного approve.
- Совпавший SHA подтверждает байты, но не готовность восстановления сервиса: для restore требуется согласованный backup, integrity check и application-level read/acceptance.

## Секреты и полномочия

Credential передаётся клиенту только как закрытый file path; секрет читает процесс. Не выводите токен, не вставляйте его в команду и не открывайте production credential-файлы. Административные и root/SSH операции не маскируйте под обычную диагностику.

## Выбор задания

Для запроса вроде «проверь зависшую задачу» сначала определите `job_id` из контекста или доступного подключённого списка заданий. Если подходящего read-only списка нет либо кандидатов несколько, запросите идентификатор или уточнение; не подставляйте произвольное задание. После выбора прочитайте статус и разрешённые артефакты текущей попытки. Сообщите подтверждённое продвижение и неизвестные поля, сохраняя read-only границу запроса.
