# Observable (OJS) в отчёте Quarto: можно, но редко нужно

Проверено прогоном: quarto 1.11.1, `embed-resources: true`, python-ядро.
Где сказано «проверено», там был собран HTML и открыт в браузере.

## Короткий ответ

Работает. OJS-ячейки живут в том же `.qmd`, что и python-чанки, и от движка
исполнения не зависят: python считается **при рендере**, OJS — **в браузере
у читателя**. Данные передаёт `ojs_define`.

Техническая преграда отсутствует. Методологическая — есть, и она в разделе
«Когда это уместно».

## Что проверено

| утверждение | исход |
|---|---|
| OJS работает при python-ядре | да |
| `embed-resources: true` не мешает | да: рантайм, `Inputs`, `Plot` вшиты, внешних `src` в HTML нет |
| страница живёт офлайн | да |
| кириллица в именах колонок и подписях | да, включая `viewof порог` |
| реактивность настоящая | да: значение изменено в браузере — таблица пересчиталась |
| Polars передаётся напрямую | **нет**: `Object of type DataFrame is not JSON serializable` |
| `.to_dicts()` и `.to_pandas()` | да |

Цена самодостаточности: страница с одной таблицей и одним графиком — около
2,2 МБ. Это разовая надбавка на рантайм, а не на строку данных.

## Как это пишется

Python считает и объявляет; OJS читает.

````markdown
```{python}
df = pl.DataFrame({"акт": ["1", "2"], "значение": [0.325, 18.0]})
ojs_define(gold = df.to_dicts())   # polars напрямую не сериализуется
```

```{ojs}
//| echo: false
viewof порог = Inputs.range([0, 6000], {value: 1, step: 1, label: "порог"})
```

```{ojs}
//| echo: false
Inputs.table(gold.filter(d => d.значение >= порог))
```
````

Две формы передачи различаются на стороне OJS:

* `.to_dicts()` — в OJS уже массив объектов, работает сразу;
* `.to_pandas()` — приходит колоночная форма, разворачивается `transpose(x)`
  (встроенная функция Quarto, подключать нечего). Экономнее на широких витринах.

Первая проще и не тянет pandas в зависимости отчёта.

## Что важно знать до того, как это попадёт в отчёт

**Данные едут в браузер целиком.** `ojs_define` кладёт содержимое витрины
в HTML. Это не выборка по требованию: фильтрует уже читатель, у себя. Отсюда
вес страницы растёт вместе с витриной, и всё отданное читатель может достать
из исходника страницы, даже если на экране показана часть.

**Внешние модули ломают самодостаточность.** `import {vl} from "@vega/…"`
тянется с сети **в момент просмотра** и в HTML не вшивается: отчёт без сети
покажет пустое место. Правило: **никаких `import` в OJS-чанках отчёта.**

**Числа в OJS не проверяются сканером прозы.** Сканер читает `.qmd` и вырезает
чанки целиком. Константа в OJS-выражении не будет поймана ничем — а стареет
она так же, как константа в прозе. Всё, что считается, приезжает из python
через `ojs_define`.

**Ошибка OJS видна только в браузере.** Дымовой рендер OJS не трогает вовсе;
`quarto render` соберёт страницу с любым выражением, а неверное имя переменной
проявится красной плашкой на месте ячейки. Проверять — открывая собранный HTML.

**Каждая ячейка — объявление, а не строка программы.** OJS реактивен: порядок
ячеек значения не имеет, имя объявляется один раз, повторное объявление —
ошибка. Это ближе к таблице формул, чем к скрипту.

## Когда это уместно

Однородность стека внутри одного `.qmd` обязательна: таблицы — `reactable`
и `great_tables`, графики — один движок. OJS был бы четвёртым набором виджетов
рядом с ними, и читатель принял бы разный вид соседних таблиц за разную их
важность.

Поэтому вопрос не «можно ли», а **что OJS даёт такого, чего не дают reactable
и графический движок**. Ответ короткий: **пересчёт от ввода читателя.** Всё
остальное — сортировка, поиск, фильтр, свёртка в группы, подсказка, разворот
строки — таблицы уже умеют, считая ширины и агрегаты на сервере при рендере.

Заводить OJS стоит, когда читателю нужно **подвинуть величину и увидеть
последствие**:

* допуск сверки: «а если считать сошедшимся расхождение до полупроцента —
  сколько находок останется»;
* порог существенности в деньгах;
* выбор уровня цен или курса приведения без пересборки отчёта.

Общее у этих случаев одно: **величина, которую методолог ещё не выбрал**,
и отчёт не вправе выбрать за него. Пока величина объявлена в модели, ползунок
ей не нужен — нужен показ объявленного.

Не заводить ради «интерактивности» как таковой: страница тяжелеет, стек
разнороднее, а числа уезжают в слой, который не видит ни сканер прозы,
ни дымовой прогон.

## Если всё же добавляем

1. Данные готовит python и отдаёт `ojs_define` — ни одной константы в OJS.
2. Никаких `import` — только встроенные `Inputs`, `Plot`, `d3`.
3. Отдавать минимальную витрину, а не «всё на всякий случай».
4. Проверять собранный HTML глазами: дым OJS не исполняет.
5. Назвать в прозе, **что именно** двигает ползунок и почему эта величина
   не объявлена в модели, — иначе читатель примет подобранный им порог
   за утверждение отчёта.
